# منهج الاختبار والقبول

## ما يجب إثباته

النجاح يعني صحة العضوية والمبالغ والإشارات والنطاق وأصل كل معلومة، لا تساوي الإجمالي وحده. يختبر كل تغيير العمل المفيد وحالات الامتناع الصحيحة معًا. لا تعطي مجموعة يرفض فيها المحرك جميع الملفات دليلًا على صلاحيته للاستخدام.

## حزمة قبول كل توسعة

| الجزء            | المطلوب قبل الإغلاق                                                                  |
| ---------------- | ------------------------------------------------------------------------------------ |
| العقد            | المدخلات والعلاقات المسموحة والرفض والمراجعة وحدود الموارد وحالات الاكتمال مكتوبة    |
| الحقيقة المرجعية | مبالغ وأعضاء وصفوف وأسباب متوقعة مستقلة عن ناتج المحرك ومثبتة قبل تقييمه             |
| الإيجابيات       | إنجاز جميع الحالات الإيجابية المقررة بأعضائها الصحيحة، لا مجرد عدم الانهيار          |
| السلبيات         | صفر اعتماد خاطئ أو إسقاط صامت أو ترقية اقتراح إلى حقيقة داخل مجموعة القبول           |
| دورة الأصل       | قراءة فعلية ← قرار ← إلغاء قرار عند الحاجة ← حفظ ← استعادة ← تصدير، مع نفس الأدلة    |
| التصدير          | فحص مستقل لقيم XLSX ونصوصه وإشاراته وأعضائه وأخطائه، مع فتح بصري عربي وإنجليزي       |
| حدود الثقة       | مصدر/سياق/رد عامل أجنبي، رد متأخر، إلغاء، تغيير القراءة، محاولة إعادة استخدام قرار   |
| الطفرات          | الاختبارات تفشل فعلًا عند إدخال خطأ مالي متعمد في نسخة مؤقتة                         |
| الاستخدام        | رفع أصلي، رسائل واضحة، دليل الوصول للمصدر، خيارات ضرورية فقط، حفظ العمل بين المجالات |
| الأداء           | قياس منفصل للقراءة والحساب والتصدير والذاكرة والإلغاء، لا زمن إجمالي مبهم            |

الأوراكل برنامج أو حقائق مستقلة تحكم صحة المتوقع؛ إعادة استخدام مكتبة الحساب نفسها لبناء المتوقع لا تحقق الاستقلال. قارئ Excel مختلف أو فحص OpenXML مفيد، لكنه لا يصحح توقعًا ماليًا خاطئًا من الأصل.

## تصميم الاختبارات التي تكشف عيبًا

- لكل قاعدة: حالة صحيحة، وحالة تختلف في دليل واحد مؤثر، وحالة منافسة تساويها في المبلغ، وحدود قبل/عند/بعد السقف إذا كان ذا صلة.
- لكل مجموعة 1:N أو N:M: تحقق العضوية الكاملة وعدم استهلاك صف مرتين، والمنافسين عبر الأدوار، والصف الخاطئ الذي ما زالت له علاقة بالمجموعة.
- تغييرات تحفظ المعنى: إعادة ترتيب الصفوف غير الحاملة لتسلسل دلالي والأعمدة، تغيير اسم الملف، RTL/LTR، رأس مكرر، فصل صفحة. يجب بقاء الحقائق والعضوية، مع تغير الإحداثيات المتوقع فقط. لا تبدل ترتيبًا يحمل معنى مثل سلسلة الرصيد الجاري وتعدّه تغيير شكل.
- تغييرات يجب أن تمنع النتيجة: تبديل العملة أو الحساب أو العلامة أو العضو أو القطع الزمني أو المصدر، وإن بقي الصافي متساويًا.
- أخطاء متأخرة: آخر صفحة وآخر صف وآخر مكون. لا نتيجة نظيفة من بادئة ملف ناقص.
- الحالة غير المثالية المعزولة يجب أن تنتج العمل الصحيح المتبقي وخطأ ظاهرًا؛ المجهول واسع الأثر يحجب اعتماد الأجزاء المتأثرة. تحدد خطة المجال إن كان يدعم العزل بالفعل.

## مجموعات البيانات

Development للتطوير، وValidation للتقييم أثناء الاختيار، وHoldout لعائلات لم تستخدم في الضبط. يقسم المصدر بحسب الجهة/القالب/العائلة، لا بحسب نسخ صفوف من القالب نفسه. نسخ CSV وXLSX وPDF من الحقائق نفسها تختبر توافق القراءة، ولا تحسب ثلاث عائلات مستقلة.

عند فشل V1 تبقى النتيجة فشلًا على V1. بعد الإصلاح تصبح الحالة Regression، ويحتاج التقييم المستقل الجديد holdout جديدًا. لا نحذف الحالات الصعبة ولا نعدل المتوقع لموافقة المنتج. العينة الاصطناعية المعلنة مفيدة لكشف الأخطاء وليست دقة ميدانية أو «تدريب نموذج».

حقيقة المولّد الخفية ليست ما يحق للمحرك استنتاجه: إذا عرف المولّد علاقة لم تظهر في الملفات فالمتوقع مراجعة، لا اعتماد آلي. امنع تسرب معرفات المجموعات المخفية إلى المصادر. سجل seed وإصدار المولّد والمدقق والعقد، وأعد استخدام [المولّد القائم](../../audit/reliability/manifest.mjs). توزيعه 2000 واضحة و1000 معقدة و1000 قراءة و500 غموض و500 غير صالحة؛ هذه خطة تغطية اصطناعية وليست توزيع السوق أو إثبات نجاح 5000 حالة.

لا يعالج عيب fixture بمجاراة المحرك: يصحح بدليل مستقل مع حفظ النسخة السابقة، ثم تعاد مقارنة قبل/بعد بالمرجع المصحح نفسه. إصلاح الاختبار لا يحسب تحسنًا للمحرك. الإلغاء والانهيار والمهلة ليست رفضًا محاسبيًا صحيحًا.

## التنوع والتحقق من أدوات القياس

يطبق [بروتوكول تنوع المصادر](../roadmap/source-diversity.ar.md) داخل C-0 والدفعة المختارة: جرد القصة والعائلة وسلالة المنتج، ثم تغيير طريقة عرض الدليل، ثم زيادة الحجم. تفصل الأعداد بين قصص مالية وبنى مصدر ومنتجين وصيغ وأحجام، ولا تدمج لتوحي باستقلال غير موجود. تشمل البطاقة مقدار المساعدة البشرية والخريطة الصريحة، والتحقق من الملف المكتوب فعلًا قبل تقييم القارئ.

توثق [DEV-16 إلى DEV-23](DEVELOPMENT-LESSONS.ar.md) حالات واقعية في تاريخ التطوير أخطأ فيها المولد أو الأوراكل أو فاحص التصدير أو مصنف الطفرات. لذلك تختبر أداة القياس نفسها بضابط موجب وتحوير خاطئ محدد؛ لا يكفي نجاح جميع مخرجات المنتج عليها. توجد حالتان مختلفتان: قصة نعرف حقيقتها، ودليل يستطيع المحرك أو المحاسب رؤيته؛ لا يطلب الاختبار إثبات علاقة لم تظهر في المدخلات.

## لوحة القياس المقترحة

هذه مقاييس مطلوب جمعها؛ ليست لوحة منفذة أو نتائج محققة حاليًا.

| المقياس                      | كيف يحسب ويقرأ                                                                                    |
| ---------------------------- | ------------------------------------------------------------------------------------------------- |
| False confirmations          | عدد الحالات المعتمدة ذات عضو/مبلغ/نطاق خاطئ؛ أي حالة في مجموعة القبول تمنع الإصدار المتأثر        |
| Exact member-set success     | عدد الحالات التي أنجزت بنفس مجموعة الأعضاء المتوقعة ÷ الإيجابيات المؤهلة                          |
| Source accounting            | جرد كل الصفوف المقروءة: مستخدم/للمراجعة/خطأ/غير حركة بسبب ظاهر؛ دون صف مفقود أو استخدام مالي مكرر |
| Scope Fit                    | الحالات الواقعية المؤهلة ÷ الحالات الواقعية المقدمة، وفق أهلية حددت قبل تشغيل المنتج              |
| Product Success Within Scope | الحالات المنجزة بمستوى القبول المحدد ÷ المؤهلة، مع فصل الآلي عن المراجع بشريًا                    |
| Review burden                | زمن المحاسب وعدد أسئلته وتصحيحاته مقابل الطريقة الحالية، على الحالات نفسها                        |
| Export/replay parity         | تطابق الحقيقة والأصل قبل وبعد الحفظ والاستعادة والتصدير، مع فصل حقول الزمن أو العرض               |
| Resource envelope            | حجم/صفحات/صفوف/خلايا، p50 وp95 للزمن، ذروة الذاكرة، زمن استجابة الإلغاء، مواصفات الجهاز           |

صفر أخطاء في عدد محدود من الحالات لا يثبت احتمال خطأ صفر. لا تنشر نسبة دقة بلا مقام وتعريف للنطاق ونوع البيانات وطريقة استقلال المرجع. يثبت هدف الأداء العددي بعد قياس baseline وقبل بدء التحسين، ولا يختار بعد رؤية النتيجة.

## تناسب حزمة الدليل مع الخطر

بوابات CI الإلزامية لا تُخفف ولا تُتجاوز في أي مستوى. ما يتناسب مع الخطر هو حزمة الدليل الإضافية التي تُبنى لكل دفعة، وعدد الوثائق التي تُحدَّث:

| المستوى | أمثلة | حزمة الدليل الإضافية |
| --- | --- | --- |
| مالي | قارئ أو تفسير أو عضوية أو سياسة أو جلسة أو تصدير مالي | الحزمة كاملة كما في الجدول أعلاه، مع holdout أعمى قبل الإغلاق |
| واجهة وتجربة | نصوص وتخطيط وتنقل دون مساس بالحقيقة المالية | فحوص المتصفح المتأثرة واللغتين والوصول، دون أوراكل مالي جديد |
| توثيق | مراجع وخطط وسجلات | اتساق الروابط والحالة وحارس النشر |

إذا مس تغيير الواجهة رقمًا أو عضوية أو حالة أو تصديرًا، يُعامل ماليًا. التصنيف يُكتب في بطاقة العمل قبل التنفيذ.

holdout الدفعة المالية يكتبه من لم يطلع على الإصلاح، وقبل رؤية نتيجته. إذا كان المنفذ نفسه هو كاتبه، يُعلن ذلك حدًّا للاستقلال، ولا يُسمى أعمى.

## الدليل العملي للإصدار

سجل SHA والشجرة وأوامر التنفيذ وبيئة الجهاز ونتائجها والعوائق. لا تنقل نتيجة تشغيل قديم إلى شجرة جديدة. الاختبارات المحددة أثناء التطوير تقلل الهدر؛ بوابات CI الحالية تبقى مطلوبة كما هي. تغيير runtime يستدعي اختبارات المجال والتفاعلات المتأثرة، وتغيير الهوية يستدعي رسم الخط الحقيقي والتنقل ومقاسات العرض، وتعديل الوثائق يستدعي صحة الروابط والاتساق وحارس النشر. فحوص CI لا تُحذف لأجل السرعة.

لا يغلق التحقق على متصفح محاكى وحده ملفات الشركات الكبيرة أو الأجهزة الضعيفة. المخرجات الخام وسجلات المستخدم تبقى خاصة؛ ينشر الملخص الآمن وروابط العقود والتشغيل فقط.
