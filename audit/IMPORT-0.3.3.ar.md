# إصلاح قراءة الملفات والتعافي — 0.3.3

## ما ثبت وما لم يثبت

أعيد إنتاج رفض PDF المرفق في الإصدار المنشور 0.3.2. يحتوي على ترويسة بنص أبيض فوق خلفية داكنة، وخلفية جدول فاتحة تُرسم بعد عنوان الصفحة وقبل نص الجدول. كان فحص الرسوم يقارن الخلفية بجميع نصوص الصفحة، بما فيها النص الذي لم يُرسم بعد، ويرفض الأبيض دون تقييم خلفيته. أدى ذلك إلى رفض كشف نصي عادي.

شوهد خطأ `Cannot read properties of undefined (reading 'sheets')` في جلسة الموقع التي أبلغ عنها المستخدم، لكن إعادة رفع Excel نجحت ولم يُعد إنتاج التسلسل المتقطع بصورة حتمية. ثبت باختبار مستقل أن العميل القديم يحوّل ردًا ذا رسالة خطأ فارغة إلى نجاح بقيمة `undefined`. عولج هذا الخلل وحدود بروتوكول العامل؛ لا ندّعي أن تصادم رسائل PDF.js هو السبب المثبت لبلاغ المستخدم.

## الإصلاح

- ربط النص المستخرج بتسلسل Unicode الفعلي لأوامر رسم النص. تعذر الربط يوقف القراءة.
- السماح بالخلفيات المستطيلة المعتمة البسيطة المرسومة قبل النص، مع فحص تباين النص مقابل الخلفية. النص الأبيض يحتاج خلفية داكنة تغطي حدوده كاملة. رسم لاحق يغطي نصًا يظل مرفوضًا.
- إبقاء ضوابط النص المخفي والشفافية والقص والأقنعة والصور والمسارات غير المفهومة. مراجعة PDF وتعيين حدوده شرطان قائمان؛ الفحص ليس إثباتًا لكل بكسل.
- إضافة قناة وإجراء وحالة نجاح صريحة إلى بروتوكول العامل، وفحص بنية الملف ومصدره قبل الوصول إلى `sheets`. الرد الفارغ أو غير الموافق للطلب لا يصبح نجاحًا.
- إنهاء العامل المتعطل وإعادة إنشائه بعد خطأ القراءة أو الإلغاء أو انتهاء المهلة؛ لا تنتقل حالته إلى محاولة رفع الملف التالي.
- دعم تواريخ صريحة مثل `02-Jul-2026` وأسماء الأشهر الإنجليزية الكاملة مع التحقق من التقويم؛ لا استخدام لـ`Date.parse` أو تخمين التواريخ الملتبسة.
- التعرف على أعمدة `Debit (SAR)` و`Credit (SAR)` والتحقق من مطابقة عملة عنوان المبلغ للعملة المؤكدة. لا يُستخدم الرصيد المتحرك بدل مبلغ الحركة.

## أدلة التحقق

نجحت محليًا 203 اختبارات، وكشفت اختبارات التحوير عشرة أخطاء محاسبية مقصودة. نجح فحص مستقل لـ18 مصنف Excel، يشمل 288 خلية رقمية ودقة الأرقام وXML وCRC والنص العربي والإنجليزي.

قُرئ PDF المرفق بعد ضبط حدود الجدول ومراجعة صف العناوين واستبعاد صفّي الرصيد والتذييل بأسباب صريحة. تحققت الحركات الـ11 دون أخطاء، وتطابقت المبالغ والإشارات والمراجع وكل رصيد متحرك مع استخراج مستقل بواسطة pypdf وعمليات Decimal. وقُرئ Excel المرفق ذو 18 ورقة. رُفع الملفان بنجاح في واجهة نسخة الإنتاج المحلية؛ لم تُعتمد مقارنة بينهما لأن نطاقيهما غير مؤكدين.

يتضمن اختبار Chromium في بوابة النشر التسلسل: PDF يغطي رقمًا يُرفض ← Excel صالح يُقبل ← PDF بترويسة ملونة يُقبل ويُراجع ← مقارنة بملف اصطناعي مقابل ← تصدير Excel والتحقق من القيم الرقمية. يعمل التسلسل دون اتصال بعد تحميل الموقع، وتفشل البوابة عند أخطاء المتصفح أو طلبات خارجية/POST. النتيجة المنشورة النهائية لهذا الاختبار تُراجع في GitHub Actions؛ كتابة الاختبار ليست ادعاءً بنجاح تشغيله.

حُفظت نتائج الإصدارات القديمة دون تعديل. كانت إخفاقات إعداد الاختبارات الجديدة هي مواضع حدود غير مناسبة في PDF اصطناعي وغياب تأكيد التغطية في اختبار الرصيد؛ صُححت العينات مع بقاء رفض التغطية الناقصة. ملفات المستخدم ومحتواها ونتائجها التفصيلية محفوظة محليًا فقط، ولم تُضف إلى المستودع. العينات المنشورة مستقلة واصطناعية.

## حدود النتيجة

هذا إصلاح للعطل الملاحظ واختبارات انحدار؛ ليس holdout مستقلًا ولا ضمانًا لدقة كل كشف. PDF المصور/OCR والرسوم غير المدعومة تحتاج مسارًا لاحقًا مدروسًا. لا تغيير في صلاحيات AI أو قواعد اعتماد المطابقات أو خصوصية المعالجة المحلية.
