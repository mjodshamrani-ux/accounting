# P4 finite currency-qualified signed header — independent pre-code draft

This is independent, synthetic contract input authored before implementing the family. It does not claim implementation, native extraction acceptance, field acceptance or financial approval. Expected economic rows are specified directly and exact minor units are computed with Python Decimal; no product import or output supplies truth. Existing families, sources and their outcomes remain unchanged.

## Scope

The source is an original text PDF with exactly four columns at the existing signed-section positions: `Date`, `Reference`, `Description`, and one literal qualified amount header. Admit only `Signed amount (SAR)`, `Signed amount (JPY)` and `Signed amount (KWD)`. Retain existing explicit invoice parent/continuation identity roles and all original row/page/cell evidence. The finite precision policy is SAR=2, JPY=0, KWD=3. The currency is original header evidence; the exponent is the contract's fixed policy, not an invented original source cell. An explicitly selected session exponent must equal the policy before a receipt or derived artifact can be minted.

The family does not add conversion, column rearrangement, monetary auxiliary columns, balances, metadata rows, split debit/credit, general currency names, free text or new financial relation authority. A fifth column, an unknown occupied row or a changed continuation header keeps the complete derivation blocked. Missing qualification on the first header does not acquire currency authority through this family; the previous bare-header family keeps its own previously accepted behavior.

## Mandatory positive behavior

All nine original positive cases must yield exactly the manually serialized CSV and full inventory after explicit section interpretation review: on-page, cross-page and explicit-row-reference cases for each of the three currencies. Preserve every signed amount literal, date, description, leading-zero invoice identity, source-to-derived link and the same qualified header. Preserve negative, positive and zero amounts; compute exact minor units under the fixed precision without rounding or losing sign. Cross-page currency evidence includes the literal amount cell of every complete repeated header, with the original physical page and row. Equal money or currency consistency creates no financial approval.

The derived CSV first row must be the exact original qualified header row. The currency cannot disappear into a bare canonical `Amount` header or an XXX context. Sidecar provenance must include one currency context with code, decimals, `precisionOrigin: finite-contract-policy`, and the source-bound qualified header cells. Each evidence item has original source SHA256, extraction SHA256/revision, sheet, physical row/page, one-based column and literal. All currency evidence must be replayed from original PDF bytes and compared with the current original reading, full inventory and session selection. The sidecar remains a declared derivation record, not standalone financial authority.

The derived native CSV must be freshly reread and prepared under the qualified currency code and matching exponent with financial/scope confirmation false. It must contain exactly the expected movements and exactly the qualified header as non-movement, with no errors and exact signed minor units. Reusing the existing original-source preparation/amount-header conflict guard is viable; passing XXX would incorrectly conflict with the qualified header. A later main-comparison use retains its normal scope-confirmation contract. A sidecar or deserialized receipt alone cannot import approval or set a confirmed financial scope.

## Refusal behavior

Every frozen blocked original refuses whole derivation: changed/missing continuation qualification; contradictory original currency row; double/unknown/ambiguous/lowercase qualification outside the finite vocabulary; unreadable late amount; JPY fractional value; SAR/KWD excess fractional precision; changed reference role; extra financial column; missing continuation; unknown late row. Partial CSV or a receipt that survives rejection is forbidden. Currency text in a description cannot become header evidence. Bare-header controls remain outside this new family, with no new currency authority; their historical bare-family behavior is not reclassified.

Every frozen action refuses stale, forged, mismatched or incomplete currency evidence: wrong explicitly selected exponent, changed cached amount header, changed original bytes, changed header row/page/column citation, source swap after review, changed reading after receipt, changed extraction revision, copied receipt, omitted continuation evidence, sidecar code/precision tamper, changed original qualified header during await, cancellation and incomplete movement selection. Original source bytes remain exact and no stale/partial artifact publishes.

## Reuse and independent acceptance

There is no existing `CurrencyContext` type or currency-header parser in `io.ts`. Its `transparentNumericFormat` guards native XLSX display semantics and cannot certify PDF/CSV currency context. `scope-inference.ts` already recognizes literal amount headers with `(CODE)` and provides original header evidence; `core.ts` rejects amount-header currency disagreement with the confirmed scope; `currency-precision.ts` supplies the finite offline precision lookup. Those are implementation reuse candidates, not expected-value oracles. The section context guard, replay provenance and UI must explicitly preserve the new finite context.

Acceptance needs an independent native shape check of every original PDF against the frozen inventory, source hashes and cuts, before implementation expectations are changed. Product errors in that first extraction are evidence to preserve, not permission to regenerate truth. Then review implementation separately, bind strict positive obligations and all refusal actions, reread native CSV independently, and test real downloads/provenance/original preservation in both interface languages. Run current-batch final gates and close that batch before implementing this contract on its separate branch.
